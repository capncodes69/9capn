# open-sse

Provider-agnostic SSE engine: one OpenAI-style request → any provider (LLM chat, image, embedding, tts, stt, search), streamed back in the client's format.

## Request lifecycle (chat)

`handlers/chatCore.js` → `services/model.js` `parseModel` (resolve `provider/model`) → **pre-translate hooks** (`rtk/` tool_result compress, `rtk/headroom.js` proxy compress, `rtk/caveman.js` system inject — all fail-open) → `executors/index.js` `getExecutor(provider)` → `translator/index.js` `translateRequest` (client format → provider format) → `executor.execute()` (streams upstream) → `translateResponse` (provider chunks → client format) → SSE out.

## Directory map

- `config/` — ALL constants/config (no hardcode elsewhere). `providers.js`/`registry/` (provider defs), `providerModels.js` (alias→models matrix), `runtimeConfig.js` (timeouts, token limits), `*Constants.js`.
- `translator/` — format conversion. `request/<from>-to-<to>.js`, `response/<from>-to-<to>.js`, `schema/` (enums: ROLE, CLAUDE_BLOCK…), `concerns/` (shared logic), `formats.js`+`formats/` (per-format). `index.js` is the registry/entry.
- `executors/` — per-provider upstream call. `base.js` (BaseExecutor), one file per special provider, `index.js` map.
- `providers/` — registry build + `capabilities.js` + `pricing.js`. Entry: `index.js` (PROVIDERS).
- `handlers/` — per-modality cores (chat/image/embedding/tts/stt/search) + sub-provider folders. `chatCore/` has the streaming/non-streaming/sse-to-json handlers.
- `rtk/` — request token-killer. `index.js` compresses `tool_result` content in-place (OpenAI/Claude/Kiro shapes); `filters/` per-tool compressors + `autodetect.js`; `headroom.js` external compress proxy; `caveman.js` system-prompt injector.
- `transformer/` — `responsesTransformer.js` (Chat Completions SSE → Codex Responses API SSE), `streamToJsonConverter.js`.
- `shared/` — cross-provider auth/identity: `clineAuth.js`, `machineId.js`, `qoder/`.
- `services/` — `model.js`, `provider.js`, `accountFallback.js`, `combo.js`, `compact.js`, `tokenRefresh/`+`tokenRefresh.js`, `oauthCredentialManager.js`, `usage/`, `projectId.js`, `kiroModels.js`/`qoderModels.js`.
- `utils/` — streamHandler, stream, sse, error, sessionManager, claudeCloaking, clientDetector, proxyFetch (patches global fetch), cursorProtobuf/cursorChecksum, ollamaTransform.

## Conventions

- Config-driven, DRY, camelCase. NEVER hardcode values, models, or block/role strings — use `config/` + `schema/` constants.
- Translator pipeline pivots through OpenAI as the intermediate format. A translator registered on the exact `source:target` pair (e.g. `claude:kiro`) runs as a **direct route**, skipping the lossy double-hop.
- Translators self-register via `register(from, to, reqFn, resFn)` as an import side-effect — new files MUST be imported in `translator/index.js`.

## How to add

- **Provider**: copy `providers/REGISTRY_TEMPLATE.js` → `providers/registry/{id}.js`; add models to `config/providerModels.js`. Generic providers need no executor (DefaultExecutor handles OpenAI-compatible APIs).
- **Executor** (only for non-standard upstream): subclass `BaseExecutor` (override `getBaseUrls`/`buildHeaders`/`buildUrl`/`execute`), register in `executors/index.js` map. `getExecutor` falls back to `DefaultExecutor` when absent.
- **Translator**: add `request|response/<from>-to-<to>.js` calling `register(...)`, then import it in `translator/index.js`. Reuse `schema/` + `concerns/` — don't re-implement parsing.

## CapnZed (Zed trial provider)

`capnzed` is 9capn's own Zed hosted-models provider, built to farm the free **Zed Pro Trial** and rotate accounts when one is spent. It shares **no code** with the upstream `zed` provider (which stays `hidden: true` and untouched) — `shared/capnzedAuth.js` + `executors/capnzed.js` are a deliberate self-contained copy so upstream can change its Zed files without breaking this one.

**Reverse-engineered wire facts** (Zed 1.19.2, `df181c6f`; from `crates/language_models_cloud`, `crates/cloud_llm_client`, `crates/cloud_api_client`, `crates/cloud_api_types`):

- **One host** `https://cloud.zed.dev` serves both the account API and the LLM API. `api.zed.dev` is the unrelated collab/RPC API.
- **Two auth schemes.** Account API/T: `Authorization: {user_id} {access_token}` (space-separated — *not* Bearer). LLM API: `Authorization: Bearer {llm_token}`, minted per-organization by `POST /client/llm_tokens` with `{"organization_id": …}`.
- **Login is RSA, not OAuth2.** Generate an RSA keypair → open `/native_app_signin?native_app_port&native_app_public_key` → browser redirects to `http://127.0.0.1:{port}/` with the `access_token` RSA-encrypted against the public key → decrypt locally (OAEP-SHA256, PKCS#1 v1.5 fallback). No client_id/secret, no refresh token.
- **`POST /completions` is a pass-through relay, not OpenAI-shaped.** Body is `{thread_id, prompt_id, provider, model, provider_request}` where `provider_request` is the raw provider-native body; `provider` ∈ `Anthropic | Baseten | OpenAi | Google | XAi`. The response is **NDJSON**, one JSON object per line, each `{"event": …}` or `{"status": …}`, terminated by a `stream_ended` status. Errors arrive as `{code, message, upstream_status, retry_after}`.
- **The trial is metered server-side as a dollar credit, not bandwidth or tokens:** "$5 of GPT Luna and unlimited edit predictions for 14 days from trial start". There is **no balance/remaining-credit endpoint** — `PlanInfo.usage` only covers edit predictions.
- **Trial exhaustion == HTTP 402** on `/completions` (the client renders it as "payment required to use this language model"). Per-account state is readable from `GET /client/users/me` → `plan.plan_v3` (`zed_pro_trial`/`zed_pro`/`zed_free`/…), `trial_started_at` (RFC3339), `subscription_period.{started_at,ended_at}`, `is_account_too_young`, `has_overdue_invoices`.
- **There is a second, per-IP gate.** "Trial access is blocked" exists only server-side (nothing in the client crate emits it), so an account needs a unique egress IP as well as unique credentials — give every CapnZed connection its own sticky proxy pool.

**Behaviour:** trial + Pro are served; everything else (`zed_free`/`student`/`business`/`vip`, too-young, overdue) is refused pre-flight and the account is parked until the trial window ends (`subscription_period.ended_at` → `trial_started_at + 14d` → `now + 30d`, clamped to 31d). A spent account locks **every model at once** (`modelLock___all`) because the credit is account-wide, and `src/sse/services/auth.js` honours the full CapnZed window instead of the generic 30-minute cap.

**Quota tracker:** the dashboard card is built from `GET /client/users/me` (plan + trial window) plus 9capn's **own ledger**, because Zed exposes no balance endpoint. `applyCapnZedSpend()` (`services/usage/capnzed.js`) folds in `getProviderSpend()` (`src/lib/db/repos/usageRepo.js`), which sums the recorded `cost` of this connection's CapnZed requests since the trial/period start — so the credit row is a **local estimate at list prices**, never Zed's number, and the card message says so. The row declares `unit: "USD"` (rendered with a `$` by `QuotaTable`) and `recurring: false` (the trial credit never refills → "expires in"). A paid `zed_pro` account has no credit to draw a bar against, so its spend is reported as text instead. Credit/day constants live in `shared/capnzedAuth.js` (`CAPNZED_TRIAL_CREDIT_USD`, `CAPNZED_TRIAL_DAYS`); the branch that preserves `unit`/`remainingPercentage` for the dashboard is `case "capnzed"` in `src/app/(dashboard)/dashboard/usage/components/ProviderLimits/utils.js` (the generic fallback drops both).

**Connecting an account.** Two paths reach the same `exchangeTokens(provider, callbackUrl, null, rsaPrivateKey, state)` call — the auto path in `lib/oauth/utils/server.js` (the local callback listener decrypts and saves by itself) and the **manual paste** in `POST /api/oauth/capnzed/exchange`. The paste is not a fallback nicety: Zed redirects the browser to `http://127.0.0.1:{port}/`, so when 9router runs anywhere other than the user's machine the redirect always fails to load and the paste box is the *only* way in. The route therefore resolves the RSA private key **from the session registered by `/register-session`** (a `codeVerifier` in the body still wins) — do not make it require `codeVerifier`/`redirectUri` like the generic authorization-code path, or every remote connect dies with "Missing required fields". `tests/unit/capnzed-connect-manual.test.js` pins this.

**Decryption must fail loudly.** `decryptCapnZedAccessToken()` tries OAEP-SHA256 then PKCS#1 v1.5, and both results are validated with `looksLikeAccessToken()` (printable header-safe ASCII, 16–8192 chars). OpenSSL 3 implements *implicit rejection* for PKCS#1 v1.5, so a wrong-key or stale callback returns random bytes instead of throwing — without the guard that garbage gets saved as a working-looking connection which then 401s/403s later with a message that points nowhere. A wrong paste must 500, never `success: true`.

**Model catalog.** `registry/capnzed.js` carries a static floor of the ids Zed's own client ships (its `agent.default_model` uses e.g. `provider: "zed.dev", model: "gpt-5.6-sol"`), because the dashboard picker needs a list before a connection exists. The **live** `GET /models` response stays authoritative and per-model (`display_name`, `provider`, `max_token_count`, `supports_images/thinking`, `supported_effort_levels`), and `passthroughModels` keeps unknown ids working. The connection page reads it through the `capnzed` entry in `src/app/api/providers/[id]/models/route.js`, which falls back to the static list with a warning when the account cannot be read. Re-derive the static list after a client update:

```
strings -n 4 -t d ~/.local/zed.app/libexec/zed-editor | grep -n "Claude Opus 5Claude Opus 4.8"
# prints the display names table, followed by the same-order id table
```

Relay-provider mapping matters because it picks the body shape: `claude*`→Anthropic, `gemini*`→Google, `grok*`→XAi, `gpt*`→OpenAi, and the open-weight families (`deepseek`, `glm`, `kimi`, `minimax`, `mimo`, `qwen`, `hy3`, `muse-spark`)→**Baseten** (Chat Completions, *not* Responses). `normalizeCapnZedProvider()` only guesses; the live catalog's explicit `provider` wins.

**When Zed updates, re-check in this order:** (1) the trial copy in `crates/language_models/src/provider/cloud.rs` (credit amount + day count — currently $5 / 14 days, mirrored in `CAPNZED_TRIAL_CREDIT_USD`); (2) `plan.rs` `PlanInfo` fields and `Plan` variants; (3) whether the 402 mapping in `language_models_cloud.rs` still marks `ProviderErrorCategory::PaymentRequired`; (4) the `x-zed-*` header names in `cloud_llm_client.rs` (including `x-zed-minimum-required-version`, which the server uses to force client upgrades); (5) the `LanguageModelProvider` enum (a new relay provider must be added to `normalizeCapnZedProvider` — `baseten` was missing upstream and silently sent to `OpenAi`, i.e. the wrong body shape).

## Camber (agent platform)

`camber` is 9capn's provider for **Camber** (cambercloud.com) — an agentic compute platform, not a model gateway: every request is driven by a server-side *agent* (`context_agent`) while the model is chosen separately. Hosted models are **Bedrock Claude**. All wire specifics live in `shared/camberAuth.js` — its header is the primary record; this section is the summary.

**Wire facts.** Base `https://api-v2.cambercloud.com/api/cli`; every answer is an envelope `{code, message, data}` and `code !== 0` is a failure. `Authorization: Bearer <api-key>`. Auth is dual: browser login *and* a pasted API key, both ending as the same bearer credential (the 40-hex key `camber login` prints, also `CAMBER_API_KEY`).

- `POST /auth/initiate` → `{"data":{"session_id":…}}`; the user authorises at `app.cambercloud.com/auth-cli?session_id=…`; `GET /auth/poll?session_id=…` answers `202 {"data":"pending"}` until it returns `200 {"data":{"token":"<base64>"}}`, whose base64 decodes to `{profile:{username,email,token}, teams}` — `profile.token` **is** the credential. There is **no user code**: nothing to type, and no callback to paste back, because 9capn polls.
- `POST /chat` serves the turn. Body: `{context_agent, content, model_name, conversation_id?, effort?, thinking_enabled?, context_agent_version?}`. The async variant is `POST /conversations/init` → `{id}` → `POST /chat` → poll `GET /conversations/{id}/status` until it leaves `running` → `GET /conversations/{id}/reply`.
- **The stream is NOT SSE.** `Accept: text/event-stream` is answered with `Content-Type: text/plain` + chunked **AI SDK v4 data-stream** frames (`f:`/`0:`/`g:`/`d:`/`e:`/`y:`/`z:`…). Parse chunked framing + prefixes, never `data:`. Text-only by design: tool frames (`9:`/`a:`/`b:`) are dropped. `d:` carries real `{promptTokens, completionTokens}` — that is what the usage ledger records.
- **`g:` is the reasoning (chain of thought) and must be forwarded as `delta.reasoning_content`.** Verified live: a `47*89` prompt streams `g:"47"`, `g:"*"`, `g:"89"`, `g:" = 47*90 -"` … before the answer. It must **not** be folded into `content` (a thinking client would render it twice; a plain client would show the model talking to itself). `i:` (redacted reasoning) and `j:` (its signature) are dropped — half a thought is not content. `y:` carries the **server-side `conversation_id`**; nothing consumes it yet (every turn re-seeds the transcript into `content`), and it is the hook if context ever moves server-side.
- **Thinking is ON unless you turn it off.** A request that sends neither `thinking_enabled` nor `effort` still emits `g:` frames, so "send nothing" is a valid choice, not a silent disable. `resolveCamberEffort()` therefore forwards only what the client actually asked for.
- **No model catalog endpoint** (13 candidate paths probed, all 404). `registry/camber.js` therefore carries a floor from the CLI's own `--model` list plus the ids the web picker sends, and the server stays authoritative (`400 Model not supported by the current plan`) — so `passthroughModels` must stay on. `effort` ∈ `low|medium|high` (the server's `oneof` rejects anything else) and is **separate from** `thinking_enabled` (bool): reasoning off is `thinking_enabled:false`, never `effort:"none"`.
- **Camber DOES meter usage — the credential is what cannot read it.** The web app's `personal-usage` page reads `GET https://api-v2.cambercloud.com/api/credit-usage/me`, which returns one entry per resource (`cpu_seconds`, `gpu_seconds`, `llm_messages`, `storage_gb` — ids read out of the `personal-usage` web chunk, alongside `/usage/teams?teamId=…` for a team card). That endpoint is scoped to the **web session**: with a CLI API key, or with no token at all, it answers `401 unauthorized - invalid token`, while the same key reads `/api/cli/me` fine. Both credentials a connection can hold (a pasted key, and the one `/auth/initiate` + poll issues) are CLI-scoped, and `/api/cli/me` returns identity only (`user_id`, `email`, `username`, `teams[]`) — no plan, no quota. **Do not add this endpoint to a fetcher**; the card says where the real meter lives instead (`CAMBER_WEB_USAGE_URL`).
- **Cold start is real:** Camber warms a sandbox before the first frame of a new conversation — measured 28s on a warm account and ~2 min on a cold one — so `transport.timeoutMs`/`stallTimeoutMs` are 300000 (headroom for the slow case), not streaming-sized values.

**A bare model is NOT reachable — but a pinned CLI agent is a trap.** Camber is an agent platform end to end: every candidate raw-inference route on the CLI surface (`/chat/completions`, `/completions`, `/messages`, `/responses`, `/v1/chat/completions`, `/inference`, `/converse`, `/predict`) answers **404**, and the web surface `/api/ai/*` refuses a CLI token with 401. There is also **no agent catalog endpoint** (`/agents`, `/agents/list`, `/agent`, `/context-agents` → 404), which is why the agent is free text, not a dropdown.

The agent is a per-connection setting (`providerSpecificData.camberAgent`, stored without the leading `@` the wire wants) whose **default is *none***: `context_agent` is left OFF the request (`CAMBER_DEFAULT_AGENT === ""`), which is what the web app's own payload does (it carries no `context_agent`, only `context_agent_version: null`). The server then runs `agent_orchestrator_tool` and picks a platform agent itself — observed returning `context_agent_name: "CamberAgent"` for a chat prompt and `"CodingAgent"` for a coding-shaped one. `CAMBER_UNPINNED_AGENT_ALIASES` (`""`, `none`, `default`, `auto`, `server`) absorbs the words users type when they mean the same thing, and `buildCamberChatBody`/`initCamberConversation` omit the field rather than sending it empty.

**A Camber agent can NEVER edit the caller's local files — do not chase this.** The agent prompt wins over anything the client sends, because it is the real system role while a client's system message is flattened into `content` as user-role text. Evidence, all live: every agent available to an account runs in a **Camber-hosted Jupyter environment**. The only two aliases that exist for the test account are `nova.cli` ("Camber CLI agent for coding environments", runs `jupyter_start_server`) and `nova.snowflake` ("Camber Snowflake Assistant … I run inside a Camber-hosted Jupyter environment … everything I touch lives in the Camber cloud environment, never on your personal computer. **NO**"). The orchestrator's own pick is no better: with `context_agent` omitted it chose `CamberAgent`/`CodingAgent`, which also writes to `./outputs/` "across multiple notebook cells". And a client cannot opt out: a forceful `[system]` block demanding local-file behaviour got `SANDBOX-ONLY` back, **with `CamberAgent` (an agent that carries no jupyter tool at all)**, so the sandbox framing is platform-level, not per-agent.

There is also no request field to switch it off. Probed against the CLI `/chat` struct with a validated oracle (send a field as `{}` behind a bogus `context_agent`: an existing field answers `Unmarshal type error: expected=<Go type>, got=object`, a missing one falls through to `404 Agent not found` — verified positive with `effort` and `thinking_enabled`): **31 candidates** — `notebook_path`, `project_id`, `agent_id`, `source_uris`, `tools`, `tool_names`, `enable_tools`, `use_tools`, `sandbox`, `no_sandbox`, `no_tools`, `mode`, `agent_mode`, `system_prompt`, `system`, `prompt`, `metadata`, `files`, `attachments`, `workdir`, `cwd`, `environment`, `env`, `notebook`, `use_notebook`, `jupyter`, `execute`, `permission_mode`, `temperature`, `max_tokens`, `stream` — **none exist** on the CLI surface. (`notebook_path`/`project_id` belong to `/api/ai/*`, the web struct, which rejects a CLI key with 401.) Aliases are `owner.name`; anything without a dot is rejected `400`, a well-formed unknown alias is `404 Agent not found`.

There is also no **client-tool channel** to route around it: `buildCamberChatBody` sends only `content`/`model_name`/`agent`/`effort` (a client's `tools` array is not forwarded), and every `9:/a:/b:/c:` frame in the stream describes a tool the **server** ran. A turn that asked for a file came back with `jupyter_start_server` then a Python cell that wrote `/home/jovyan/projects/<Title>-<YYYY_MM_DD-HH_MM_SS>/probe-artifact.txt` — the sandbox path convention, useful when reading an agent's prose about where it put something.

**What DOES work: asking for content instead of an edit.** Asked to *print* a minimal HTML file in one fenced block and to write no file and use no notebook cell, the agent complied in 7.4s with no tool call beyond the orchestrator's router. So the honest workflow is "model returns the content, the caller saves it" — not "model edits my disk". For anything that needs real local file edits, the caller must use a provider that exposes a raw model plus its own tools.

One web-surface exception worth knowing: `/api/ai/agents/community` answers **200 without any credential** (it is the public community-agent catalog), while `/api/ai/conversations`, `/api/user/ai/agents` and `/api/ai/conversations/chat` answer `401 unauthorized - invalid token` for a CLI key. The community list is still a list of Camber agents, so it offers no raw-model route.

Pinning the CLI agent `nova.cli` — the old default — **hijacks the model's identity**: the orchestrator reports `context_agent_name: "nova.cli"`, and the model introduces itself as *"Camber CLI agent for coding environments"*, offers `--api-key $CAMBER_TOKEN` and looks for files in a **Camber sandbox** instead of the caller's editor. That is why an agent that drove local tooling behaved like a different, less capable assistant. An explicit alias still wins, because some accounts genuinely want that agent's tools/skills; the fix is the default, not the feature.

**Quota tracker:** since the server side is unreachable, the only number this card owns is **9capn's own tally, and one request served = one LLM message** — Camber's own unit, so the count is comparable to the plan grant. The route (`withCamberLocalMessages` in `src/app/api/usage/[connectionId]/route.js`) windows `getProviderSpend()` (it returns `requests` as well as `cost`) and folds it in with the pure `applyCamberMessageCount()` (`services/usage/camber.js`). The **limit is a per-connection choice** — `camberPlan` (`student`/`pro`/`teams`, grants in `CAMBER_PLAN_LIMITS`) or an explicit `camberMessageLimit`, with `CAMBER_LLM_MESSAGE_LIMIT` as an operator default — never a hardcoded table, because observed grants differ from the published pricing rows (a Pro **trial** came with 500 messages where paid Pro publishes 200). With no limit configured there is **no bar at all**: a denominator nobody verified would be a fabricated claim, so the count is reported as text and the plan options are named instead. The window defaults to the current calendar month (UTC, matching Camber's "usage this month") and `camberPeriodStart` pins it for a trial, which also flips `recurring:false` so the UI says "expires in" rather than "resets in". Everything the card shows is labelled a local count; Camber's number is the authoritative one. `case "camber"` in `ProviderLimits/utils.js` is what preserves `remainingPercentage`/`recurring` for the dashboard — the generic fallback drops both.

**Provider art:** the dashboard resolves provider icons from `public/providers/{id}.png` (`ProviderIcon` → `getProviderIconSrc`), so a provider with no file falls back to its text badge **for the whole session**. Camber's is the 128x128 PNG8 in that directory, the same convention as the rest of the set.

**When Camber changes, re-probe in this order:** (1) the `/chat` frame prefixes and the `d:` usage field names — in particular that a thinking prompt still yields `g:` frames (if they vanish, the prefix set is stale, and thinking will silently disappear from every client); (2) the accepted `effort` values — send a bogus one and read the `oneof` error, which lists the legal set (that is how `low|medium|high` was confirmed); (3) whether `/models` or a **credential-readable** quota path has appeared (re-run the probe list in the `camberAuth.js` header — and note that a 401 rather than a 404 on `/credit-usage/me` is what tells you a route exists but rejects CLI keys); (4) `/auth/initiate` + `/auth/poll` status codes and the base64 blob shape — a change here breaks login **silently**, which is why `decodeCamberLoginToken()` validates the shape and 502s rather than saving a blank connection; (5) whether the plan grants moved (cambercloud.com/pricing → `CAMBER_PLAN_LIMITS`).

## Pitfalls

- A `registry/{id}.js` entry is in the **client** bundle (`src/shared/constants/providers.js` → dashboard shell). Import only *import-free* modules from it (e.g. `shared/camberCatalog.js`); importing a wire layer drags `proxyFetch` in, and `next build` then **fails** on `Module not found: Can't resolve 'net'` / `UnhandledSchemeError: node:assert` — the Fly deploy runs that build, so this is a deploy-blocker, not a warning. `tests/unit/camber-wiring.test.js` guards every file in the directory.
- `OAuthModal` keeps a **hardcoded** `deviceCodeProviders` list while the route serves `/device-code` for anything whose provider declares `flowType: "device_code"`. A provider missing from that list dies on Connect with "uses device-code login but is not wired in the OAuth modal device-code list". The two must agree — the wiring test derives the list from `PROVIDERS` and fails on either a missing or a stale entry.
- OpenAI bridge is lossy (thinking, non-base64 images, tool ids, is_error) — prefer a direct route for fragile pairs.
- `registry/index.js` is an auto-generated static import list; regenerate it (don't hand-edit) after adding a `registry/{id}.js`. REGISTRY_TEMPLATE is excluded by design.
- Special binary/protobuf formats (kiro EventStream, cursor protobuf, commandcode NDJSON) don't round-trip through OpenAI — handle in their executor.
- `rtk/` + `headroom.js` mutate the request body in-place and are **fail-open**: any error returns null and leaves the body untouched — never throw out of them. RTK skips `is_error`/`status:"error"` tool results to preserve traces.
- `proxyAwareFetch(url, options, proxyOptions)` takes proxyOptions **third**; passing a `signal` there silently drops the connection proxy. For IP-gated providers (zed/capnzed/freebuff) that means egressing from the wrong IP. Always pass `proxyOptions` explicitly on every call.
- CapnZed mints the LLM token per Zed **organization** and gates on the account's plan, so `providerSpecificData` must carry `userId`, `systemId` and `organizationId` — a connection missing `userId` cannot even read its own quota.
- Freebuff's session tier is bound to the egress IP, so `handlers/chatCore/proxyGuard.js` forces `strictProxy` (a failing pool must throw, never fall back to direct) and refuses a request with no pool/relay/legacy proxy. `FREEBUFF_ALLOW_DIRECT=1` opts out of the refusal only.
